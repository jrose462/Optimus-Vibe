**What this is:** a Windows tool that detects which of your machines it is running on and, whenever a game launches, writes
that machine's graphics preset into the game's config files (and can switch the display mode and NVIDIA driver profile),
so a desktop and a handheld stop overwriting each other's settings.

## How it's built and maintained

The bug-fix loop is **automated by Claude** and GitHub Actions, with a human merge at the end:

1. In the app, **Report a problem** files a *public* GitHub issue (as you if signed in, otherwise anonymously via the app).
   GitHub Actions labels it and queues it right away (no Claude involved).
2. **Claude audits the queued reports once a week** (Thursdays, 00:01-09:30 Pacific, at most 10 a week, oldest first). It
   gives each a verdict and, for a clear small bug, a plan. Maintainers can also run it on demand.
3. For a clear small bug, **Claude implements the plan** and GitHub Actions opens a fix PR on a `claude/*` branch after
   checking the patch against a policy (automatic).
4. Cards move on the [Optimus-Vibe - bug squashing](https://github.com/users/jrose462/projects/5) board
   (Reported, Planned, Fix in PR, Fixed, Released) automatically.
5. **CI** builds and runs 600+ tests on Windows for every PR (automatic).
6. The **maintainer reviews and merges** (branch protection; human).
7. A **tagged release** is built and published by CI/CD, and **the app updates itself**.

Game presets are generated by Claude (the `game-settings-recommender` skill) into each user's own private config repo.
Full flowchart and details: [docs/pipeline.md](docs/pipeline.md); the maintainer's weekly routine (Thursday squash, auto-merge, reviewing PRs, when to test on a real device, releasing): [docs/maintainer-guide.md](docs/maintainer-guide.md); setup: [docs/ci.md](docs/ci.md).

## Overview

Per-device game graphics settings for Windows. If you play the same games on more than one machine (say a desktop and a
handheld), each needs different settings, and Steam Cloud keeps syncing one machine's config onto the other.
Optimus-Vibe detects which machine it is on and, every time a game launches, writes that machine's chosen preset (a
Claude-recommended one or your own manual save) into the game's config files. It can also switch the display
mode and set NVIDIA driver profiles. Your settings live as YAML in **your own config repo or folder**, never in this
repo (see [Two places](#two-places-the-app-and-your-settings)).

It finds your games by itself: installed games from Steam, Battle.net, EA app, Xbox app, Epic and GOG show up in
the app's library, are managed automatically (Steam launch options included), and games it has no settings for
yet are queued for Claude to research.

It works like Apollo/Sunshine prep commands: apply before launch, undo the temporary parts (display mode) after exit.

## Install

**Download:** grab `OptimusVibe.exe` (and optionally `optimus-vibe.exe`) from the
[latest release](https://github.com/jrose462/Optimus-Vibe/releases/latest), put it in `C:\Tools\Optimus-Vibe\` and run it.
Each release also has a `.sha256` file if you want to verify the download (`Get-FileHash OptimusVibe.exe`).

> **"Windows protected your PC" / Unknown publisher:** the exes aren't code-signed yet, so Windows SmartScreen warns
> on the first run of a file downloaded with a browser. Click **More info → Run anyway**. You only see this once per
> download; in-app updates are downloaded by the app itself and don't trigger it. Code signing is planned.

**Build from source:** requires the .NET 8 SDK. Published exes are self-contained, so target machines need no runtime.

There are two exes, built on the same core:

| Exe | Needed on | Used for |
|---|---|---|
| `OptimusVibe.exe` | **every machine** | The app (no arguments), and the Steam launch-option wrapper (`run …`, headless: no window, no console flash) |
| `optimus-vibe.exe` | optional (desktop) | Command line for scripting and for Claude (`inspect`, `validate`, dry runs) |

```powershell
dotnet publish src/OptimusVibe.App -c Release -o C:\Tools\Optimus-Vibe
dotnet publish src/OptimusVibe.Cli     -c Release -o C:\Tools\Optimus-Vibe   # optional CLI
```

Use the same path on every machine (`C:\Tools\Optimus-Vibe\`). Steam launch options then look the same everywhere.

## Two places: the app and your settings

| Place | Role |

## First run: where should your game settings live?

The first time you open `OptimusVibe.exe` it asks one question, "Where should your game settings live?":

- **GitHub** (recommended; also the easiest on a handheld, no git needed): sign in with a short code (open
  github.com/login/device, enter the code, approve), then either **Create my config repo** (a new private repo, default
  name `optimus-vibe-config`, filled with the starter config and cloned) or **use a repo you already have** (the app
  offers to set it up if it is empty).
- **A local folder**: pick your own git checkout of a config repo, or any folder. A folder with no Optimus-Vibe settings
  is offered the starter set (`<folder>\config`). Make it a git repo yourself if you want it synced between machines.

Then run `optimus-vibe detect` (or look at Settings) and edit `config\devices.yaml` so your machines match: the starter file
has two neutral examples, `desktop` (matched by an NVIDIA GPU wildcard) and `ally-x` (matched by CPU `*Z2 Extreme*`).
On your other machines, choose the same GitHub repo (or clone the same repo and point the app at it).

## Setting up each machine

There are two ways to get the config onto a machine (the **sync provider**):

| Provider | Use on | How it syncs |
|---|---|---|
| `git` | a machine with git and a checkout | `ConfigRoot` is your own git checkout; the app runs the git CLI to commit, pull and push |
| `github` | a handheld, or any machine without git | the app keeps its own copy under `%LOCALAPPDATA%\OptimusVibe\repos\<owner>\<name>\` and syncs it through the GitHub API after you sign in. No git, no clone |

### With GitHub (no git needed)

1. Copy the published `C:\Tools\Optimus-Vibe\` folder to the machine (same path everywhere).
2. Open `OptimusVibe.exe`, choose **GitHub**, sign in and pick your config repo. CLI equivalent:
   `optimus-vibe github login` (or `github token <PAT>`), then `optimus-vibe github use <you>/<repo>` or
   `optimus-vibe github create optimus-vibe-config`; `optimus-vibe github status` shows what it is using.
3. Check detection (`optimus-vibe detect`, or the device shown in Settings).

### With a local folder or git checkout

1. Clone your config repo (or make a folder).
2. Open `OptimusVibe.exe` and choose **A local folder**, or run
   `optimus-vibe setup --config-root <your config repo>\config`. Either writes `%LOCALAPPDATA%\OptimusVibe\settings.json`,
   which stays local and is not in git. If detection picks the wrong device, add `--force-profile <device>`; the app offers
   this too.
3. `optimus-vibe detect` shows the hardware strings and the matched device; then `optimus-vibe list` and `optimus-vibe validate`.

The config root is found in this order: `--config <dir>`, `OPTIMUSVIBE_CONFIG`, the `github` provider's managed copy
(when that provider is selected and the copy exists), `settings.json` `configRoot`, then a `config` folder next to the exe
or in a parent of the current directory (handy when you run the CLI inside your config repo). To go back from `github` to a
checkout: `optimus-vibe sync-provider git`.

If you upgrade from a version that used this app repo as the config repo, the app clears that old choice once and asks
the first-run question again.

### GitHub sign-in

The `github` provider and the repo picker need a GitHub token, stored in Windows Credential Manager
(`OptimusVibe:github`). Two ways to get one:

- **Device-code sign-in** (first-run screen, Settings → Sign in with GitHub, or `optimus-vibe github login`): the app
  shows a code; open github.com/login/device on any device, enter it, approve. Official builds carry the Client ID of the
  Optimus-Vibe OAuth App, so there is nothing to set up. If a build has none (or you want your own app), register a GitHub
  OAuth App with **Device Flow enabled** at github.com/settings/developers and give the Client ID (public, not a secret) via
  Settings → GitHub client id (`gitHubClientId` in `settings.json`), the `OPTIMUSVIBE_GITHUB_CLIENT_ID` environment variable,
  or the `OptimusVibeGitHubClientId` build property (precedence: settings, env, built-in). The app asks for the `repo`
  scope, so private config repos work.
- **Personal access token**: create a fine-grained PAT (github.com/settings/personal-access-tokens) with access
  to just your config repo and **Contents: Read and write**, then paste it in Settings or run
  `optimus-vibe github token <PAT>`.

Settings lists the repos you can push to (`optimus-vibe github repos`). `optimus-vibe github logout` removes the token.

## Presets and manual saves

Each game has two kinds of settings per device, shown as two tabs in the app:

- **Recommended** presets, written by Claude (`presets:` in `config/games/<game>.yaml`). A desktop-class device gets
  `quality` (best visuals at a smooth framerate: DLSS Quality/Balanced, RT where affordable) and `performance`
  (toward the display's refresh cap: DLSS Performance, RT off). A handheld gets `performance` (60+ fps sustained,
  FSR/XeSS from 1080p, VRR) and `battery` (30/40 fps cap and the cheapest playable settings; pair it with the
  handheld's silent power mode, since Optimus-Vibe cannot set TDP). Each preset has a label, a short description, and a target fps.
- **Manual saves**, made by you: tune the game in its own menu, then save the result under a name. A save records
  every setting the game's presets know about (files with no mapped keys are copied whole). Saves live in
  `config/saves/<game>/<device>/<slug>/` and are committed and pushed automatically, so they follow you to the
  other machine's checkout.

Which settings a launch uses: the preset you picked (in the app or with `use`) is remembered per game per
device; until you pick one, the device's `defaultPreset` from `devices.yaml` applies (e.g. `quality` on a desktop, 
`performance` on a handheld).

## The app

`OptimusVibe.exe` opens on your **Library**: every installed game it detected, plus configured games that are
not installed here. On the Ally (and small screens) it is a controller-first full-screen grid: **A** play,
**X** presets, **Y** sync, **Menu** settings (`libraryMode` in `settings.json`: `auto`, `grid` or `list`).
Playing from the app applies the game's active preset, then starts it through its launcher.

For each game, pick a preset in the **Recommended** tab or one of your **Manual saves**; the choice is remembered
for this device. From the Manual saves tab you can save the game's current settings, update, rename, or delete a
save. Saves are synced through the selected sync provider (git or GitHub).

**Settings** holds the GitHub account and config repo, the sync provider, which launchers to scan (`scanStores`),
whether to write Steam launch options, and the device override.

**Check for updates** looks for a newer release of the (public) app repo and, if there is one, downloads and verifies it
(the same as `optimus-vibe update-app`; `--check` only looks). No sign-in is needed; if GitHub is rationing anonymous
requests from your network the app says so and you can try again later. **Report a problem** asks for a description and
shows a preview of the report (version, device, recent log, with tokens and your user folder redacted) before anything is
sent. The panel tells you who it is filed as: "Filed as @you" when you are signed in to GitHub (you get the notifications),
otherwise "Filed anonymously via Optimus-Vibe" through the app's built-in, issues-only access (official builds; at most 5
reports a day per machine). A build with neither copies the report to your clipboard and opens a prefilled GitHub issue page in your browser (`optimus-vibe report-bug`, with `--dry-run` to print instead). Issues are public. Reports sent by the app are queued
for Claude's weekly bug squash (Thursdays, Pacific time): Claude audits them and, for clear small fixes, implements a PR that CI tests before the maintainer merges it. See [docs/ci.md](docs/ci.md).

## Library: auto-detect, opt-out, request queue

- **Detection**: the app scans Steam, Battle.net, EA app, Xbox app, Epic and GOG (`scanStores` in
  `settings.json`) and matches each install to `config/games/<id>.yaml` by `steamAppId`, then `storeIds`
  (battlenet / ea / epic / gog / xbox), then name.
- **Managed by default**: a detected game with presets for this device is *managed*: its preset is applied every
  time it launches through Optimus-Vibe. Statuses: Managed, Needs presets, Opted out, Not installed.
- **Opt-out**: don't want Optimus-Vibe touching a game? Opt it out in the app or with
  `optimus-vibe opt-out steam:1285190` (`opt-in` reverses it). The key is `store:id`. Opt-outs are stored in
  `config/library.yaml` and synced, so they apply on every machine. Opted-out games launch plainly and their Steam
  launch option is removed. When a game's config says its settings do **not** cloud-sync
  (`cloudSyncsSettings: false`, e.g. Borderlands 4), the app suggests opting it out: each machine already keeps
  its own settings. The suggestion is never applied automatically.
- **Settings sync check**: each game page has a "Settings sync" card saying whether its graphics settings travel
  between your machines, how sure it is, and why. Evidence comes from three places:
  - **Steam Cloud**: the game's `remotecache.vdf` (e.g. "Steam Cloud syncs 4 .sav files but not
    GameUserSettings.ini").
  - **EA app**: its CloudSync log (e.g. Jedi: Survivor's `GameUserSettings.sav` is synced).
  - **What actually happens**: after each managed session Optimus-Vibe fingerprints the settings files; if they
    changed while it wasn't running and now match the *other* device's preset, the game is proven to sync
    ("settings arrived from your Ally"). After 5+ clean launches it leans towards "per machine".
  Epic, GOG, Battle.net and Xbox can't be inspected, so they rely on observation. If the evidence contradicts the
  game file's `cloudSyncsSettings`, the card shows an orange dot and recommends keeping the game managed.
  `optimus-vibe cloud-check [<game>] [--all] [--json]` prints the same report; `validate` warns about games whose
  sync status is unknown.
- **Filters**: two rows of pills above the covers, combinable. The first row is the status (All, Tuned, Needs presets,
  Opted out; LB / RB on a controller switch it). The second row, **Settings sync**, shows whether a game's settings
  travel between your devices, with the same answer the game's page gives: *Stays on device* or *Syncs* (from the
  check on this device, else from the game's research; settings seen arriving from another device always count as
  *Syncs*) or *Maybe* (neither the check nor research has an answer yet). Every pill shows its count (the status pills hold the tuned / waiting / opted-out totals; a small chip beside the "Library" title names this device), and each tile carries a small cloud, device or question-mark
  glyph with the reason as its tooltip. On a controller, press D-pad down from the status pills (or up from the first row
  of covers) to reach the sync row.
- **Request queue**: an installed game with no config is added to `config/requests.yaml` (store, id, name,
  install folder, exes, device) and synced. Ask Claude to "process Optimus-Vibe requests"; it works through the
  queue with the `game-settings-recommender` skill, one commit per game, removing each entry as its config lands.
  `optimus-vibe library` lists what was detected and its status; `optimus-vibe library --queue` also queues
  missing games.

## Game lab: Claude researches presets for you

The game lab adds or refreshes a game's presets without you running anything: the app collects evidence from this PC, files an
issue in your **private** config repo, a GitHub Actions workflow there has Claude research the game with your own Claude
subscription, the result is validated and merged automatically, and the app pulls it. Details, limits, costs and privacy:
[docs/game-lab.md](docs/game-lab.md).

Set it up in **Settings > Game lab**, a step-by-step wizard you can re-run any time:

1. **A config repo on GitHub** (the GitHub account provider, or a git checkout with a GitHub remote).
2. **Sign in with the extra permissions** (`workflow` installs the lab workflow, `project` keeps a private board).
3. **Request labels**, 4. **Install the lab workflow**.
5. **Claude token**: run `claude setup-token` in a terminal and paste it; it goes to GitHub as an encrypted secret and is never kept on the PC.
6. **Daily cap and model** (default 5 runs a day, Sonnet), 7. **Repository settings**, 8. **Project board** (optional), 9. **Test request** (optional).

Once set up, each game's page offers **Request presets**, **Refresh presets** and **Re-check settings sync** (you see what would be
sent first, and that it goes only to your config repo), plus a status chip with a link to the issue. In the background the app answers
"needs evidence" follow-ups, starts queued requests and shows "New presets for ..." when a result lands. New games without presets are
requested automatically (toggle in the same section); without the lab they are queued in `requests.yaml` as before.

**New presets arrive by themselves.** With *Settings > Sync > Auto-update presets* on (default), the app pulls your config repo on
start, every 15 minutes, when you come back to the window, and, for at most about 5 seconds, just before a game starts.

**After you quit a game** that changed its settings, a full-screen, controller-friendly prompt offers **A** Save, **Y** Save as...,
**B** Don't save, **X** Don't ask again for this game (turn it back on from the game's page). It closes without saving after 2 minutes.

**Offline.** Bug reports and game-lab requests made without a connection are saved on this PC and sent by themselves when you are
back online (the app checks when the network returns, after you sign in and every 5 minutes). A **N waiting** button appears in
the header while anything is waiting; click it to see the items, **Send now** or **Discard** one. From the command line,
`optimus-vibe outbox list` shows them and `optimus-vibe outbox send` sends them.

## Appearance

Settings → **Appearance** picks the colours for this machine: **Default** (navy and teal), **Majestic** (black and gold)
or **Circuit** (blue-black with cyan and green, faint circuit traces and a green glow on controller focus). Each card
previews its page, card and accent colours, works with mouse, touch and gamepad, and applies at once without a restart.
The choice is saved per machine in `settings.json` (`theme`: `default`, `majestic` or `circuit`). The palettes are the
`Themes\Palette.*.xaml` files; a new one only needs the same keys.

## Devices

Settings → **Devices** edits `config/devices.yaml` (it syncs like `library.yaml` when Sync automatically is on):

- **Add this device** looks at this machine (CPU, GPU, model, computer name, current display mode) and fills the form:
  handhelds are matched on the CPU, desktops on the GPU model, and if another device already matches this machine the
  computer name (`machine`) is added to tell them apart. Change the name, the match rules (key/value rows), display mode,
  driver (NVIDIA, AMD, none, or auto), default preset and **Use presets from** another device before saving.
- The **id** (the `devices.yaml` key, kebab-case) can only be chosen when a device is created: presets and saves are filed
  under it. **Rename** changes the display name (`name:`) only; the name is what the app shows everywhere, the id is the
  fallback.
- **presetsFrom**: a device can name another device whose presets it uses for games that have none of their own (one
  level, no loops; `validate` reports unknown or looping `presetsFrom`).
- The first device whose rules fit wins, so use the up and down arrows to order them. Deleting a device (with a
  confirmation) leaves its presets and saves in the repo; they are just not used. Comments and the order of the rest of
  the file are kept when the app edits it.
- After a change the app re-detects this machine and tells you if it now matches a different device.

On the command line: `optimus-vibe devices list`, `devices add <id> --name <n> [--match key=value ...] [--presets-from <id>]
[--from-this-machine]`, `devices rename <id> <name>` and `devices remove <id> [--yes]`.

## Big Picture (TV)

When a big TV is in use, games that have a `big-picture` preset for your device switch to it automatically, the
display mode is set on the TV for that launch, and it is restored when the game exits. It activates when:

- **the TV is docked**: an active display that is 16:9 and at least 3840 px wide (and is not the device's own `display`
  mode, so a 5120x2160 ultrawide never counts), or whose monitor name matches your `match.name`; for example the
  Ally X plugged into a 4K TV; or
- **a 4K stream arrives**: Apollo/Sunshine (Moonlight client) exports `SUNSHINE_CLIENT_WIDTH`, `_HEIGHT`, `_FPS`
  and `_HDR` (Apollo also `APOLLO_CLIENT_*`) to the launched app, and a client asking for at least 3840 px wide counts.

An explicit `--preset` (or a preset picked for that launch) always wins; `--no-big-picture` skips detection. A game without a
`big-picture` preset keeps its normal one and the log says "No Big Picture preset for <game>; using ...". In the app a
**TV** badge appears in the header (tooltip: why), the game page lists **Big Picture (TV)** first marked "Auto on TV", and
**Never use Big Picture for this game** (or `optimus-vibe tv opt-out <game>` / `tv opt-in <game>`) opts one game out on
this device.

```powershell
optimus-vibe display list     # active displays: device name, monitor name, mode, primary
optimus-vibe tv status        # is Big Picture active, and why
```

Everything is optional; add a `bigPicture:` block to a device in `devices.yaml` to tune it:

```yaml
devices:
  desktop:
    bigPicture:
      preset: big-picture            # preset name used on the TV (default)
      display: { width: 3840, height: 2160, refresh: 120 }   # fallback mode if the preset sets none
      match:
        name: ["LG TV*", "SONY TV*"] # monitor names from `display list` (one pattern or a list; * and ?)
        minWidth: 3840               # size test and stream test (default 3840)
        aspect: "16:9"               # size test (default)
        stream: true                 # also activate for a 4K stream client (default)
```

Moonlight users can also force it per app by adding `--preset big-picture` to the Apollo app's command.
The desktop streams at the client's resolution, so no `match` is needed there.

## Commands

Global options: `--config <dir>` (config root), `--profile <device>` (override detection),
`--preset <name | manual:<slug>>` (use this preset for one command instead of the remembered one).

| Command | What it does |
|---|---|
| `run <game> [--no-prompt] [-- %command%]` | Back up, apply the active preset, set display + driver profile, launch, wait for the game's processes, restore the display, then offer to keep settings you changed in-game as a manual save |
| `apply <game> [--dry-run]` | Apply without launching; `--dry-run` prints a per-key diff |
| `presets <game>` | List recommended presets and manual saves for this device (`*` = active) |
| `use <game> <preset \| manual:<slug> \| default>` | Remember which preset the game uses on this device (`default` = back to the device default) |
| `save <game> <name> [--update <slug>] [--notes <text>] [--no-activate] [--no-sync]` | Save the game's current settings as a manual save (and make it active, and commit/push, unless told not to) |
| `delete-save <game> <slug>` | Delete one of this device's manual saves |
| `sync` | Commit manual saves, pull, and push the config repo (through the selected sync provider) |
| `library [--queue] [--stores <list>] [--json]` | List detected games with their `store:id` key and status; `--queue` adds games without a config to `config/requests.yaml`; `--stores` limits the launchers scanned (`steam,battlenet,ea,xbox,epic,gog`) |
| `devices list` / `add <id> --name <n> [--match k=v ...] [--presets-from <id>] [--from-this-machine]` / `rename <id> <name>` / `remove <id>` | Edit `config/devices.yaml` (comments and order kept; ids never change) |
| `opt-out <key>` / `opt-in <key>` | Stop / resume managing a detected game (`key` = `store:id`, e.g. `steam:1285190`); stored in `config/library.yaml` |
| `steam-options [<game>] [--enable \| --disable \| --skip \| --unskip \| --sync-all] [--dry-run] [--exit-steam]` | Show or change the Optimus-Vibe wrapper in Steam launch options (Steam must be closed to write; see "Steam games") |
| `github login [--client-id <id>] \| token <PAT> \| repos \| use <owner/name> [--branch <b>] \| create <name> [--public] \| logout \| status` | GitHub sign-in (device code or PAT), list repos you can push to, select or create the config repo and switch to the `github` provider, sign out, show the current setup |
| `sync-provider git \| github` | Choose how the config repo syncs on this machine: a git checkout (the `configRoot` folder) or the app's GitHub copy |
| `restore <game> [--original \| --timestamp <stamp>]` | Roll the game's files back from a local backup; with no flag, lists the backups (newest first) and changes nothing |
| `version` | Show this build's version |
| `update-app [--check]` | Update `optimus-vibe.exe` (and `OptimusVibe.exe` next to it, unless it's running) from the latest release of the app repo; `--check` only reports whether a newer release exists |
| `report-bug <description> [--game <game>] [--dry-run]` | File a bug report on the app repo, or print it with `--dry-run` (same as **Report a problem** in the app) |
| `outbox list` / `outbox send` | Show or send the reports and game-lab requests that were saved while offline |
| `display list` / `tv status` / `tv opt-out <game>` / `tv opt-in <game>` | Active displays with monitor names; whether Big Picture (TV) is active and why; per-game opt-out (see "Big Picture (TV)"). `run` and `apply` take `--no-big-picture` |
| `detect` | Show detected hardware and the matched device |
| `inspect <game> [--full]` | Show resolved paths, current values vs the active preset, and file contents |
| `list` | List configured games with the active preset, available presets, and number of manual saves |
| `validate` | Check devices.yaml, every game file, and every manual save |
| `update` | Pull config changes from the repo (git checkout or GitHub, per `sync-provider`) |
| `shortcut <game> [--out <dir>]` | Create a .lnk that runs the game through Optimus-Vibe (for non-Steam games) |
| `setup [--config-root <path>] [--force-profile <device> \| --clear-force]` | Per-machine setup (stored in `%LOCALAPPDATA%\OptimusVibe\settings.json`) |

Examples:

```powershell
optimus-vibe presets cyberpunk2077
optimus-vibe use cyberpunk2077 performance
optimus-vibe save cyberpunk2077 "Steady 40" --notes "Medium crowds, 40 cap"
optimus-vibe apply cyberpunk2077 --profile ally-x --preset battery --dry-run
```

## Steam games

Every managed Steam game needs this launch option (Properties → Launch Options):

```
"C:\Tools\Optimus-Vibe\OptimusVibe.exe" run cyberpunk2077 -- %command%
```

**The app writes it for you**: for every managed Steam game it sets the option (keeping anything else you had
there), and removes it again when you opt a game out. Steam overwrites its config while running, so the app only
writes while Steam is closed: it offers to close Steam itself, writes the options, reads them back to check them and
reopens Steam (or it writes them the next time Steam is not running). To manage
launch options yourself, turn this off in Settings (or `"writeSteamLaunchOptions": false` in
`%LOCALAPPDATA%\OptimusVibe\settings.json`); `optimus-vibe steam-options` shows and applies the changes by hand.

**Choose which games get it**: when changes are waiting, the banner has a **Review…** button listing each game with a
checkbox, its launch option before and after, and whether its graphics settings sync between your devices (with the
confidence: *Syncs between devices · high confidence*, *Maybe syncs · not known yet*, *Stays on this device · medium
confidence*, *· from research*). Games that sync or might are ticked by default; games confirmed on this device
(medium or high confidence) to keep their settings there start unticked.
**Apply selected** closes Steam, writes only the ticked ones, checks them and reopens Steam.
Unticked games (and any game whose page has *Keep Steam launch option up to date* switched off) go to
`steamLaunchOptionsSkip` in `config/library.yaml` (synced), so Optimus-Vibe never touches their launch option, whether
to add or remove it. From the CLI: `optimus-vibe steam-options <game> --skip` / `--unskip`; `--sync-all` respects the list.

The id after `run` is the game id (the YAML file name under `config/games/`). Steam starts the wrapper, and the
wrapper starts the game. With `run` the app opens no window and no console; output goes to the log (see below). `optimus-vibe.exe run`
does the same from a terminal, but flashes a console window when Steam starts it.

## Non-Steam games (Battle.net, EA app, Xbox, Epic, GOG)

The simplest way is to start them from the Optimus-Vibe app (library → A), which applies the preset and then
starts the game through its launcher. Outside the app they have no `%command%`. The game file's `launch:` block says how to start them, e.g. Battle.net with
`--exec="launch Pro"` (Overwatch) or `--exec="launch Fen"` (Diablo IV). The app's **Launch game** button runs them
through the wrapper. Or create a shortcut (it targets `OptimusVibe.exe run <game>` when the app is next to the CLI):

```powershell
optimus-vibe shortcut overwatch --out "$env:USERPROFILE\Desktop"
```

Launch the game from that .lnk, or add it to Steam as a non-Steam game so it also works from the Ally's
full-screen experience.

## Tuning settings in-game

You don't need Claude (or YAML editing) to change a game's settings:

1. Launch through Optimus-Vibe and change settings in the game's menu.
2. On exit, if any tracked setting changed, a prompt asks whether to keep the changes as a new manual save (or
   to update the manual save you are using). Answer Yes and it becomes the game's active preset on this device.
   Answer No and the active preset is re-applied next launch.
3. Or save any time with `optimus-vibe save <game> "<name>"` or from the app's Manual saves tab.
4. To go back to a recommendation: pick it in the app or `optimus-vibe use <game> default`.

Manual saves are committed and pushed automatically (turn this off with `"autoSync": false` in
`%LOCALAPPDATA%\OptimusVibe\settings.json`; then run `optimus-vibe sync` yourself). Run `optimus-vibe update`
(or `sync`) on the other machine to pull them. Each device only uses its own saves.

## Backups, restore, logs

- Before writing, the tool backs up every file it touches to `%LOCALAPPDATA%\OptimusVibe\backups\<game>\`:
  `original\` (the first state ever seen, kept forever) plus timestamped folders (`yyyyMMdd-HHmmss`, last 10).
- `optimus-vibe restore <game> --original` returns to the very first state; `--timestamp <stamp>` restores a specific
  backup (the folder name). Without a flag it only lists the backups.
- Logs: `%LOCALAPPDATA%\OptimusVibe\logs\`. Run state used for crash recovery: `%LOCALAPPDATA%\OptimusVibe\state.json`.

## Device detection

`config/devices.yaml` (in your config repo) lists devices with `match` rules on `model`, `manufacturer`, `cpu`, `gpu`, or
`machine` (computer name), using `*`/`?` wildcards, plus a free-text `description` of the hardware (Claude reads it when
recommending settings). The first device whose rules all match wins. Virtual display adapters from
Apollo/Sunshine/GlideX/Parsec are ignored. Match a handheld on its CPU (e.g. `*Z2 Extreme*`) rather than an AMD GPU name,
because a desktop with an AMD CPU also reports a Radeon iGPU. Run `optimus-vibe detect` to see the strings to match. Override
with `--profile <device>` or `setup --force-profile <device>`.

## Driver settings

- **NVIDIA (desktop)**: the `nvidia:` block in a game preset (e.g. `FrameRateLimiter: 162`) is written to the
  driver's per-application profile for the game's exe via NVAPI DRS. It persists like a setting made in NVIDIA
  Control Panel and is not undone on exit.
- **AMD (Ally X)**: AMD has no supported API for Adrenalin per-game profiles. The plan is to apply ADLX *global* 3D
  settings (Chill, RSR, AFMF, Anti-Lag...) on launch and restore them on exit. **Not implemented yet**: `amd:`
  blocks are ignored. See [docs/amd-adlx.md](docs/amd-adlx.md).

A vendor block on the wrong hardware is skipped.

## Safety

- Only game config files, registry values listed in a game's YAML, the display mode, and driver profiles are
  changed. The tool never touches game memory or game binaries and does not inject anything, so it is safe with
  anti-cheat.
- Every write is preceded by a backup; the display mode is restored on exit, and after a crash on the next start.

## Troubleshooting

- **"This machine matches no device"**: run `optimus-vibe detect` and adjust `match` in `devices.yaml`, or
  `setup --force-profile <device>`.
- **Settings don't stick**: the game may rewrite its config on boot. Try `readOnlyAfterApply: true` for that file,
  and check `notes:` in the game's YAML. Some games store settings server-side (some Blizzard keys).
- **Wrong machine's settings after a sync**: launch through the wrapper (Steam launch option / shortcut). Plain
  launches skip Optimus-Vibe. Make sure options that differ per device are set in every preset.
- **"Cannot write JSON path" / key not found**: the key name is wrong for this game version. Run
  `optimus-vibe inspect <game>` and fix it (look for `# TODO verify` comments).
- **Display didn't switch back** (wrapper crashed or was killed): the next `optimus-vibe run` detects the stale
  state and restores it first. Otherwise set it in Windows display settings.
- **No visible output from a Steam launch**: check `%LOCALAPPDATA%\OptimusVibe\logs\`.
- **Undo everything for a game**: `optimus-vibe restore <game> --original`.

## Upgrading from GameProfiles

This project was called GameProfiles (`gameprofiles.exe` / `GameProfilesApp.exe`). On first start the app or CLI copies
`%LOCALAPPDATA%\GameProfiles` to `%LOCALAPPDATA%\OptimusVibe` (settings, selections, backups, GitHub mirrors, logs),
clears a config repo setting that still points at the app repo (the app repo no longer holds config; you are asked again where your settings live), copies the GitHub token to the new
Credential Manager entry `OptimusVibe:github`, and leaves the old folder and credential in place (delete them when
you like). The old `GAMEPROFILES_*` environment variables are still read when the `OPTIMUSVIBE_*` one is unset, and
Steam launch options that still point at `GameProfilesApp.exe` / `gameprofiles.exe` are rewritten to `OptimusVibe.exe`
by `steam-options` / the app. Download the new `OptimusVibe.exe` and `optimus-vibe.exe` from the releases page.

## Adding games

Installed games are queued automatically (see "Library" above). Open Claude Code **in your config repo** and ask it to
"process Optimus-Vibe requests" to work through the queue. For a game that is not installed yet, or to redo one, ask:
"add <game> to Optimus-Vibe" or "refresh recommendations for <game>". It follows the `game-settings-recommender` skill
(`.claude/skills/game-settings-recommender/` in this repo; copy it to `~/.claude/skills/`), which researches the game's
settings, reads your devices from `config/devices.yaml`, confirms key names with `optimus-vibe inspect --config <config repo>\config`,
writes the presets, validates and commits **in your config repo**. See [CLAUDE.md](CLAUDE.md) for the rules (written for
Claude but readable by people) and `config/games/_template.yaml` (in your config repo; the starter copy is
`seed/config/games/_template.yaml` here) for every field. In VS Code with the YAML extension, game files are validated
against `config/schema/game.schema.json` as you type.
